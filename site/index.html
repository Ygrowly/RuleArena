      四条不变量，四个跑出来的缺陷

      不变量是约束，缺陷是实测产物。四个缺陷都不是想出来的，每一个都补了回归测试。

      INV-AAgent 不知道门禁存在

      不 import 门禁任何符号（含 TYPE_CHECKING），门禁的理由码也不进它拿到的结果。

      INV-B门禁只做确定性算术

      读快照、读回执、比金额。不做语义判断、不调用模型、不写业务状态，用依赖白名单静态检查。

      INV-C任务成功与无资损分开统计

      终态正确不等于没多退钱，两个指标并列报，都是必过项。

      INV-D门禁不决定终态

      门禁只拦、放行或转未知。多退了钱必须由 Oracle 在权威状态上算出来，预算检查与违规判定不混为一谈。

      缺陷 1业务拒绝被读成了成功

      沙箱对业务拒绝返回 HTTP 200 加 REJECTED，工具层最初只看状态码，让裸跑组在 4 张工单上自述成功。

      缺陷 2504 没走恢复路径

      等过沙箱延迟的调用方会先收到 504，被当成硬失败抛出，而那张回执就躺在库里。

      缺陷 3正确的重试反而被拦

      网关原先固定按预算、回执、生效的顺序走，于是「再发一次同一个键问结果」被当成新退款拒绝。现在先问回执。

      缺陷 4门禁的理由码泄给了 Agent

      结果里带着 REFUND_BUDGET_EXCEEDED 这类字符串，等于告诉调用方有个门禁、而且它刚说话了。

      这些数字的边界

      • 它是 15 张工单上的一个对照，不是「绝对安全」。门禁挡住这一类失败， 不等于能证明任何 Agent 都没问题；没发现问题的说法只能表述为「在给定预算内没发现」。
      • 被测环境是真实业务系统的替身，不是任何客户的系统。它替代客户系统， 是为了让验证这件事成立，同时把危险动作关在笼子里。
      • 被测 Agent 是确定性策略，不接模型。这是刻意的：先把对照跑成立、让失败面可复现， 再考虑换成模型，否则差异说不清是门禁起作用还是模型随机。
      • 门禁的预算检查镜像的是忠实实现的边界。在一个本身就允许超额退款的环境里， 它会比沙箱更早拦住。对门禁来说，这是正确的错法。

      RuleArena：让模型去搜人想不到的路径，让确定性程序去证明路径是不是真的有问题。 本页数据由 scripts/export_refund_gate_demo.py 从一次真实运行导出。

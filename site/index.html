Agent 调了工具，却无法确定业务上到底成功没有——工具超时了，钱可能已经退了。它当成失败重试， 一笔退款就变成两笔。RuleArena 把这件事做成可复现的对照：同一份 Agent 代码、同一批工单，跑两次，一次让它自己重试，一次在网关后面加一道只做确定性算术的门禁。

问题不在 Agent 笨，在两个通道不同步

这是 2026 年被形式化为「非原子工具调用」的一类失败，也是本项目全部设计的起点。

响应通道

Agent 收到的回执：成功、失败、超时、空响应。它只能看见这个。

效果通道

服务端真正发生的事：钱退没退、账本记没记。它看不见。

两者不同步时，最常见的反应就是重试——而重试正好是重复退款的生产线。下面的工单里， 第一笔退款其实已经入账，只是回执丢了；Agent 看不到答案，换了个幂等键又退了一次。

      • 回执丢失组必须同时声明第二个缺陷轴。忠实实现自己会拒绝第二笔超额退款， 单靠"回执丢失"退不出第二笔钱，Oracle 也就无从判定资损。这是让失败可观察的必要条件， 写在每张工单的构造说明里。

      它凭什么可信

      四条不许违反的不变量，和四个靠"真跑一遍"才发现的问题。

      INV-AAgent 不知道门禁存在

      Agent 包不 import 门禁包的任何符号（含 TYPE_CHECKING）， 门禁的理由码也不会出现在它拿到的结果里——否则它可以学着绕开。

      INV-B门禁只做确定性算术

      读快照、读回执、比较金额。不做语义判断、不调用模型、不写业务状态——用依赖白名单静态检查。

      INV-C任务成功与无资损分开统计

      终态正确 ≠ 没多退钱，两个指标并列报、都设成必过项。

      INV-D门禁不决定终态

      门禁只会拦、放行或转未知；"这笔钱确实多退了"必须由 Oracle 在权威状态上算出来。预算检查与违规判定不能混为一谈。

      缺陷 1业务拒绝被读成了成功

      沙箱对业务拒绝返回 HTTP 200 + status: REJECTED， 工具层最初只看状态码。首轮实测里裸跑组因此在 4 张工单上"自述成功"，而聚合指标看着完全正常。

      缺陷 2504 没走恢复路径

      等待超过沙箱延迟的调用方会先收到 504，被当成硬失败抛出——而那张回执就躺在库里。 这是既有测试在真实沙箱上跑出来的。

      缺陷 3正确的重试反而被拦

      网关原先固定按"预算 → 回执 → 生效"的顺序走，于是"再发一次同一个幂等键问结果"—— 唯一正确的恢复方式——被当成新的退款拒绝了。现在先问回执：一次已经存在的写入不是新的写入。

      缺陷 4门禁的理由码泄给了 Agent

      结果里带着 REFUND_BUDGET_EXCEEDED 这类字符串， 等于告诉调用方有一个门禁、而且它刚说话了，违反 INV-A 的运行时语义。

      四个都是跑出来的，不是想出来的，每一个都补了回归测试。README 与 docs/agent-gateway-spec.md §8 里记录了完整过程。

      这个数字的边界

      • 它是 15 张工单上的一个对照，不是"绝对安全"。门禁把这一类失败挡住， 不等于这套系统能证明任何 Agent 都没问题。没有发现问题的说法，只能表述为"在给定预算内没发现"。
      • 被测环境是真实业务系统的替身，不是任何客户的系统。它替代客户系统， 是为了让"验证"这件事成立，同时把危险动作关在笼子里。
      • 被测 Agent 是确定性策略，不接模型。这是刻意的：先把对照跑成立、让失败面 可复现，再考虑换成模型——否则差异说不清是门禁起作用还是模型随机。
      • 门禁的预算检查镜像的是"忠实实现"的边界。在一个本身就允许超额退款的环境里， 它会比沙箱更早拦住——对门禁来说，这是正确的错法。

      RuleArena：让模型去搜人想不到的路径，让确定性程序去证明路径是不是真的有问题。

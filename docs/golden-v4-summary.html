golden-v4 度量修正记

这一轮没有让搜索变得更聪明。它做的是让「发现率」这个数字第一次说出真话—— 结果是数字变小了，但每一个都站得住，而且不可复现这件事终于看得见了。

一、数字说了谎

这三处不是代码崩溃，而是仪表读数错误——程序照常运行、照常出报告， 只是报告里的数字不指向它声称指向的东西。

01标签不可归因

声称某个 case 没被发现，说明搜索能力不足。

实际同一 scenario 下的所有漏洞 case 共用一个 能表现该 scenario 全部缺陷的环境，因为环境由一个布尔量 sandbox_version 决定。于是一条搜索路径可以踩中 B case 的缺陷， 却被记在 A case 的标签下。golden-v3 的 Multi 运行里因此有 3 条 Oracle 已确认的违规被计为未命中，Single 的分母也退化成 8。

修法把布尔量换成 7 个缺陷轴， 每个漏洞 case 显式声明它要测的那一个；Sandbox 只让声明的轴生效，并 拒绝本 scenario 触达不到的轴（422，而不是静默失效）。

02「最近一次 benchmark」是测试写的

声称接口返回最近一次完成的评测。

实际latest_completed() 只按时间排序， 所以一个测试为验证持久化而写的单 case 运行压过了所有真实套件运行。 库里共有 15 条这样的行。更要紧的是：我第一次把它改成「按 case 数排序」， 结果让老的 48-case golden-v2 运行压过了当前的 21-case v4——矫枉过正。

修法在非碎片中取最新，并把 MIN_SUITE_CASES 的语义写进 docstring：这是碎片过滤， 不是完整性证明——一个被截断的多 case 运行仍然能通过它。 判断一个运行是否覆盖了整个套件需要声明的 case 数，那是 Release Gate 的职责。

03报告把两个版本拼进一张表

声称报告标题写着 golden-v3，表格就是 golden-v3。

实际导出器按 (suite, baseline, version, seed) 分组各取最新， 但打印时只按 baseline 成行。于是 v4 已测的 Random / BFS 行与 v3 的 Agent 行 出现在同一张表里——两个版本的 case 环境不同，数字不可比， 而这正是版本号存在的全部理由。

修法--benchmark-version 锁定单一版本 （默认取最新完成的运行），缺的格子渲染为 N/A，不借用别的版本的数字。

二、仪器坏了

这四处不改变结论，但会让结论来路不明——包括我自己写来防止出错的那些东西。

04我自己的隔离矩阵在断言不可达的组合

实际修完 01 之后，我给 Sandbox 加了「拒绝不可达的轴」。 紧接着我自己那张单位矩阵当场红了——它一直把 PROMOTION 的 run 拿去过 REFUND_POINTS 的探针，而那些组合此前是被静默忽略的。

修法矩阵收窄到该 scenario 真实可达的轴 / 探针对。 更有价值的是范围变了：从「跨 scenario 不串」变成 「同 scenario 内不串」——后者才是真正会发生的那种混淆。

05resume 是坏的

实际从 Postgres 读回已完成的 case 时， attack_run_id 是 UUID 对象，而模型要的是字符串。 只有走到重放边界的运行才有这个字段，所以三个搜索基线从来没碰过这条路径。 hidden 跑到 45/51 被中断，--resume 第一次读 case 就撞上。

修法重建时把驱动返回的 UUID 转回字符串， 并加一条纯函数测试。这是被真实运行发现的，不是被测试发现的。

06用例生成器硬编码了版本号

实际生成器为新 case 写死了一个 scenario version， 与套件里既有的不一致。运行器在启动时拒绝了整个套件 （「同一 scenario 的 case 必须共享同一个规则与 scenario 版本」）。

修法版本一律从套件本身读取，而不是在生成器里重复一遍； 并在 loader 加载期就拦住不一致的套件——原先只有运行器会拦， 那已经是写完套件很久之后了。

07迁移元数据漂移

实际迁移给 attack_run 加了 defect_axes 列，但 SQLAlchemy 的 table metadata 没同步声明。 alembic check 因此提议删掉这一列—— 下次谁跑一次 autogenerate，就会生成一条破坏性迁移。

修法在 metadata 里补上声明，两个 alembic check 恢复干净。

  • 搜索不可复现，这是本轮最重要的发现。 hidden Multi 的 pass@3 = 8/14 (57%)，但 pass^3 = 1/14 (7%)——8 个被找到的 case 里，只有一个三次都找到。 「57% 的时候能找到」和「7% 的时候能稳定找到」是两个完全不同的产品承诺， 而单次运行的 v3 把这两者压成了一个数字。
  • Multi 5/14（36%）高于 BFS 2/14（14%），但置信区间仍然重叠 （[16–61%] vs [4–40%]）。按统计口径仍不能宣称谁更强。 要把两者分开需要更多 case 或更多重复——这是量化的下一步依据， 不是把阈值调低。
  • 四基线全部 0 次 INFRA_FAILED。 并且 UNPARSABLE_OUTPUT 现在是具名终止原因而非整条运行失败： 模型偶发输出不可解析时，记为该策略正常终止，不再污染发现率的分母。
  • 门禁判定：拒绝。9 项检查过 8 项，唯一未过的是 hidden_discovery_at_least_75_percent（8/14 = 57% < 75%）。 与早期版本的本质区别在于：那时门禁不可能通过 （发现率上界被动作空间裁到 60%），现在是真的没找够。

四、仍然不知道的

  • dev 只有单次运行。pass^k 只在 hidden 上有。 这是一个明确的取舍：dev 的 rep 3 要再花约 90 分钟，而 dev 的结论是四基线之间的 横向比较，那个比较靠 Wilson 区间已经站得住。表里的 reps 列如实写着 1。
  • hidden 只跑了 Multi-strategy。另外三个基线在 hidden 上没有数字， 报告里渲染为 N/A，不用别的版本的数填。
  • 碎片过滤不是完整性证明。一个多 case 但被截断的运行仍会通过 latest_completed()；真正的判断依据是 Release Gate 按版本元组比对。
  • 15 条单 case 合成运行仍在 control 库里。 它们是 append-only 的（触发器强制），我没有为了干净而弱化那个约束。
  • 真正未做的还有两块：规范化状态投影与差观测闭环 （让 Agent 能比对"规格说的"与"实现做的"），以及探针归一化预算 + 确定性上界基线。这两块才是提升搜索能力的方向。

验证状态：ruff · mypy · pytest（121 passed / 39 skipped）· 两个 alembic check 全绿， 工作树干净。缺陷轴的验收测试跑在真实 Sandbox 上，不是 mock： 每个 case 的 ground truth 必须在它自己声明的轴下确认，在忠实环境下不确认， 在同 scenario 的兄弟轴下也不确认。
